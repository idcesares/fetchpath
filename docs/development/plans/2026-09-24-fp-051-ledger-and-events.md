# FP-051: command ledger, revisions and event sequencing in the session

**Goal:** The session carries out protocol v1 commands through an in-process `EngineClient`, following [the job contract](../../architecture/JOB-CONTRACT.md) §5 and §8: deduplication by `(client_id, command_id)` against a durable ledger, acknowledgement only after the change commits, optimistic revisions, per-job `seq` with replay-or-snapshot subscriptions, and coalesced progress. Fix findings F2 and F3 from [the characterization](../ENGINE-SESSION.md).

**Constraints:** 0.1.0 queue files load and still re-serialize unchanged; the desktop keeps calling the session directly and behaves as before, apart from F2 and F3 and the batch fix below, each changed on purpose with its test. No transport (the pipe is FP-052, the engine host FP-053). Strong-model review of persistence ordering before done.

## Decisions

1. **Ledger and events live in the queue file.** `queue-v1.json` gains an optional `engine` object: the queue-wide cursor, the retained durable events, and the ledger. Records gain `jobRevision`, `lastSeq` and the last durable state they were reported in, omitted while zero. One temp-file-and-rename save therefore commits a command's change, its ledger entry and its events together; a separate file could not. Readers that do not know the fields ignore them, so the schema version stays 1.
2. **Commit path.** `Engine::execute` holds a command lock, so ledgered commands run one at a time. It looks the command up first (contract §5: identity before time validation), checks `issued_at` for an unseen one (10 minutes old at most, 2 minutes in the future; ledger retention 12 minutes), checks `expected_revision`, then marks the queue "defer saves" and runs the existing session method. Saves inside the method, and any other thread's saves meanwhile, only mark the state dirty. Then the ledger entry is added and one save commits everything, and only then is the reply returned. A crash before that save leaves no trace of the command, so resending it is safe; a crash after it returns the stored result on resend.
3. **Events are derived at commit.** At every save, each record is compared with the last durable view recorded for it: a new record is `job_created`; a changed state is `state_changed`, plus `error_recorded` when it failed and `publication_completed` when it completed; a changed schedule is `policy_changed`; a removed record is `job_removed`. Each event takes the job's next `seq`, the next queue `cursor`, and advances `job_revision`. Every path produces them the same way: commands, the poll, automatic retry, restart recovery. Commands correlate their events with their `command_id`.
4. **Retention.** The last 512 durable events are kept. `SubscribeJob(after_seq)` replays when the job's retained events reach back to `after_seq + 1`, and `SubscribeQueue(after_cursor)` likewise; otherwise the reply is a `SnapshotBoundary` with atomic snapshots and the position they reflect.
5. **Subscriptions.** Replay is computed and the subscriber registered under the queue lock, so no event falls between them. Each subscriber has a bounded queue of durable events (1,024); one that falls that far behind is closed with `resource.subscriber_lagging` and resubscribes from its last `seq` or `cursor`. Progress samples are coalesced per subscriber (latest per job), so a stalled reader costs memory bounded by the number of jobs and never delays the engine.
6. **Ticking.** `Engine::tick` reconciles the queue (starting, finishing and retrying jobs), commits resulting events, and samples progress for running jobs. The in-process client runs it every 250 ms on a background thread; FP-053's engine host will do the same. The desktop keeps driving reconciliation through its poll.
7. **Mapping to the protocol.** Session snapshots map to protocol snapshots: `scheduled` is `queued` with `not_before`; `needs_source` is `waiting_for_source` with a reason. Session errors become `ProtocolError`s by the command that raised them: an unknown job is `contract.unknown_job` (checked before the method runs), a refused state change `contract.invalid_transition`, bad input `input.invalid_request`. Commands the session cannot do yet (`SelectMedia`, `RefreshMediaChoices`, `ReplaceExisting`, `retain_partial`) answer `contract.unsupported`.
8. **F3: actions from codes.** A failure's code is its leading token: `family.name` from the core, `name` from the media adapter (read as `media.name`), or `internal.unknown` when there is none. The action comes from a table keyed by that code, not from searching the message. The HTTP status of `source.transfer_failed` is read only from the fixed `HTTP status NNN` detail the transport writes, until the core reports it structurally. Snapshots carry the code (`errorCode` on the desktop's interface, `error.code` in the protocol).
9. **F2: unknown is not retryable.** Only transport codes (`source.transfer_failed` other than a 4xx refusal, and a failure to start) are retried automatically. `internal.*` and unrecognized codes keep a manual Retry for a person but are `retryable: false` in the protocol and are never retried on a timer.
10. **F4 (found while planning): batches are all or nothing.** Every link in a batch is validated before any is queued. Today a batch that fails on its second link has already queued its first.

## Tests

The contract's adversarial list for this layer: duplicate commands (same result, one job); the same id with a different payload (`contract.idempotency_conflict`); expired and future `issued_at`; two clients racing on one revision; replay after reconnect, with and without compaction; a subscriber that never reads while downloads run; a crash after commit but before the reply (reload, resend, same result, no duplicate); a failed commit (nothing durable, resend works). F2, F3 and F4 each change their characterization test on purpose.
